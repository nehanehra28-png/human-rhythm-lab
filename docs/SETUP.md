# Connect the app to real accounts

The local preview is ready to explore. These steps are needed before inviting real testers.

## 1. Supabase: accounts, progress, and media

Create a Supabase account and a project. In a test project first, run `supabase/migrations/001_initial.sql` in its SQL editor. The migration creates tables, ownership policies, an atomic check-in save function, and a private media bucket. Do not run it over an existing unrelated database.

Copy `.env.example` to `apps/web/.env.local`. Add the project URL and publishable key; add the service-role key only to the server variable. Keep the file private. Configure email delivery and the app URL in Supabase's allowed redirect URLs. Disable public sign-ups: this is invitation-only.

The sign-in screen sends and verifies six-digit email codes only. In Supabase Authentication → Sign In / Providers → Email, set Email OTP length to **6**. In Authentication → Email Templates → Magic Link, replace the body with `supabase/templates/magic-link.html` and set the subject to "Your Human Rhythm Lab sign-in code". The template displays `{{ .Token }}` and contains no login link or `{{ .ConfirmationURL }}`. Saving a template file in this repository does not apply it to hosted Supabase; save these changes in the dashboard. Keep the Invite User confirmation link for first-time activation. Public signup remains disabled and OTP requests use `shouldCreateUser: false`. Existing passwords are not erased by this UI change. Configure SMTP and exact app redirect URLs.

Verify six-digit email delivery, invalid/expired/reused codes, resend limits, session restoration, uninvited accounts and the dashboard after sign-in in a test project. Live OTP checks have not been executed.

## 2. Media and content

Use Experience studio to write and save drafts, add a video/transcript and infographic/description, then publish. Supported uploads: MP4/WebM video and PNG/JPEG/WebP images, up to 50 MB each. Larger video needs a resumable/streaming solution. Uploaded objects stay private; members can access media attached to unlocked published experiences. External HTTPS URLs can also be used, but third-party hosts control their access and playback.

Do not publish the hydration sample unchanged without the program team's qualified content review. No hydration calculator or diet prescription is generated by the app.

## 3. OpenRouter and weekly reviews

Create an OpenRouter account, add your server-only key, choose a supported model with JSON-output support, and set a spending limit. Verify provider data practices before using participant data. Set OPENROUTER_MODEL explicitly; no paid requests were made during development.

Set a strong CRON_SECRET. The /api/reviews endpoint accepts only that secret, uses structured scores/responses (not notes), and processes up to four reviews per daily invocation. Three check-ins are the provisional minimum for a reflection. A week completes when the participant's local program day advances beyond its final day. A daily 06:00 UTC job queues eligible reviews; arrival can be delayed by up to a day or longer if the cohort exceeds the batch capacity. For larger groups, replace this bounded pilot job with a scalable queue before launch.

Failed reviews stay visible as a failure message. Admins can queue them for retry; the next job processes them. The daily schedule is in apps/web/vercel.json. Cron availability and execution limits must be checked for the chosen Vercel plan.

## 5. Before inviting testers

Use two test participant accounts and one admin account to verify isolation, private notes, draft/future content restrictions, invitation/OTP flows, uploads, and one bounded AI call. Confirm local versus shared-time unlocking, group size/start date, privacy disclosure, retention/deletion requests, and final feedback visibility. Automatic retention deletion and self-service export/deletion are not implemented yet. Review clinical program content separately.

Production build and browser preview checks do not verify Supabase policies or real provider behavior. Do not enter real participant data until these checks pass.

## Personal timelines (7 October 2026)

Existing projects must run `supabase/migrations/002_personal_timelines.sql` in the Supabase SQL Editor after migration 001. Copy the SQL contents, not the file path. New projects run both migrations in order. The app deliberately reports a setup error until migration 002 is applied, so browser and database permissions cannot disagree about unlocked days.

New memberships start when the admin sends the invitation. Day 1 is the invitation's local calendar date in the member's timezone (initially UTC until confirmed). Next days unlock at local midnight; changing timezone can shift the calendar boundary, but cannot replace the stored invitation timestamp. Existing members with recorded check-ins, reviews or feedback retain their prior day mapping. Existing members without recorded activity start at migration time. Re-running migration 002 does not reset starts.

Shared published content, the shared diet plan and meeting settings remain group-wide. Individual call scheduling is not implemented. Test two accounts invited on different dates, future-content/media denial, check-in boundaries and personal weekly review eligibility before launch.

## Multiple check-ins

Apply `supabase/migrations/003_multiple_checkins.sql` after migrations 001 and 002 before deploying the multiple-check-in UI/API. Every explicit Add check-in appends a private timestamped mood, energy, sleep and note entry and atomically updates the existing daily summary. Habit changes update only that summary. Weekly charts and AI continue to use the latest daily summary, so frequent check-ins do not inflate completed days. Existing records are preserved without invented historical timestamps.

Cloud verification still required: save two entries on the same day, refresh and confirm both remain; confirm another participant and admins cannot read entry notes/history; confirm future/out-of-program day inserts fail; confirm habit updates do not append entries.
